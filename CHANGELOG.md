#### Tooling
- **Conformance suite `suiteVersion` 0.2.3 → 0.2.4** (patch position: added cases, pre-1.0). 209 → 215 vectors, 157 → 163 fixtures, 366 → 378 checks. A fixture pins what a READER reports; a vector pins what a CANONICALIZER produces, and the behaviour above is the canonicalizer's — before these vectors a third-party implementation that still merged inside `attributes` passed every published vector while computing a different document ID. Each canonical form was hand-derived from the §4.3 rules and its JCS bytes and digest generated by the independent Python oracle, then reproduced by the TypeScript canonicalizer through the adapter protocol. `caption` needs BOTH a merge vector and a reject vector: a merge vector alone cannot catch an implementation that scopes the run rule more narrowly than the merge, since both scopes yield the same bytes for a document that merges; the reverse mutant is caught by the merge vector alone. **`hints` and `preamble` get a vector and a fixture each, and the reason is worth recording.** Both declare their `items` as `$defs/block`, and a `block` DISPATCHES `type:"text"` to `$defs/textNode` in its first `allOf` branch — so “resolves to `block`” IS “resolves to `textNode`” whenever the element is a text node, exactly as the root `blocks` array does. Reading the `$ref` as “blocks only” is a natural and wrong inference, and it was made here: an earlier draft of this entry asserted on that basis that neither rule could fire at those positions, while a schema-valid `academic:exercise` with a split combining sequence in `hints` was being REJECTed. Measured before the fix: dropping `hints`, `preamble` or `content` from BOTH transcriptions at once left every gate green except `check:block-content-positions`, so half the position set rested on the derivation gate alone. `hints` and `preamble` now have four guards each. `content` deliberately keeps only that one guard: it is the position where the merge and the run rule diverge, and pinning today's behaviour would publish an expectation #121's sequel is scheduled to change. All eight fixture content parts were schema-validated against `content.schema.json` with negative controls, which no gate does. That check is why an earlier attempt was wrong: it authored the `attributes` control through `attributes.hist`, which `blockAttributes` forbids (`additionalProperties: false`), making the artifact that pins “canonicalization rejected a conformant document” itself non-conformant. `semantic` is the only place under `attributes` an array of text-shaped objects can sit. `conformance/errors.json` stays at **v0.14 / 86 codes**; `CDX-E-PART-STRING-NOT-NFC`'s `note` is rewritten to state the run arm's third condition, position — an implementer building from the registry alone would otherwise over-report and fail the new CLEAN fixture. The file's `compatibilityPolicy` permits a note rewrite with no version bump.

That makes it an integrity suppression rather than a reporting gap. The NEGATIVE CONTROL places the boundary: the pre-canonicalization scans and the raw-byte hash still fire at any depth, so the silence is exactly the canon-gated passes and "a deep document loads clean" is true only of one carrying nothing those scans catch. The bound counts CONTAINERS, so the block figure is shape-dependent — it moves a whole blockquote depending on where the referencing mark sits — and is not reproducible from itself. **Three `test-document-verdict` cases** pin it: the hashed anchor position, the out-of-hash annotation position, and the id collision, that last one because `documentVerdict` deliberately orders the reference pass BEFORE the id recompute so a duplicate id surfaces as its own finding, and past the bound that ordering buys nothing. Each SEARCHES for the boundary rather than hard-coding it, so the pin stays tied to the constant; each carries a FLOOR, the defect being reported below the bound before its absence above means anything; and each carries a LIVE WITNESS — a non-NFC string, scanned by an iterative walk with no depth guard — that still fires above the bound. The witness is the part worth keeping: without it "reports nothing" is equally satisfied by a reader that never managed to read the part, and the assertion cannot tell a silence from a failure to load. An unknown block type does NOT serve, `classifyContent` carrying its own bound over block LEVELS and going silent around 256 blockquotes. Assertions are set EQUALITY, catching in one comparison that the gated code is gone, the witness remains, and nothing was swapped in. One arm lands a document at EXACTLY the bound: a blockquote contributes two containers, so the chain steps in twos and straddles the bound without landing on it, leaving the guard's comparison untested on the one value that separates `>` from `>=` — tightening it by one was measured to pass every gate in the repository. An empty `marks` array shifts the parity by a single container and closes it. Mutation-verified: disabling the depth bound fails all three, silencing the witness fails all three, and tightening the guard by one now fails the arm written for it. **Two of #114's four items are withdrawn, and a third is reclassified.** Item 1, the concatenation scope fix, stays withdrawn to #121. Item 4, stating that a text leaf node is admissible as a root-level block, goes to #122: three drafts were each measurably wrong — "permitted in any array that holds block content" contradicts §7.2 rules 3, 4, 5, 7, 8 and 9; the schema-derived enumeration contradicts §7.2 rules 6 and 11 ("MUST be block-level content") and §4.12.1, which makes text-in-`tableCell` an OPTIONAL shorthand that SHOULD NOT be used; and the enumeration is under-inclusive against fourteen extension-schema arrays resolving to the same unconstrained `$defs/block`, one of which is the very array #121 turns on. The schema's silence is not the specification's permission. Measured: deleting any one of the four arms B1b-3c-1a added — the root envelope, the stored-byte text scan, the anchor-position pass and the out-of-hash annotation position — left every gate green, and each deletion made `confirm_clean` return "clean" rather than being caught by a later arm. Where an arm returns a tagged set — the classifier's six block/mark tags, the four reference tags, the three position rows — each tag gets its own row. Thirty-six arms are driven from the malformed corpus; the thirty-seventh, the archive-unreadable guard, is driven from synthetic bytes, no document fixture being an unreadable zip. Crucially the table does not merely restore coverage but RATCHETS it: the arms are enumerated from the function's own AST and the drivers traced, so an arm added later with no row fails the selftest instead of being silent — without that, inserting a new arm was measured to leave every gate green, which is precisely how the four arms above came to be unmutatable. Selftest failures now accumulate rather than returning on the first, so one rotted fragment reports the others in the same run. Building the table surfaced a latent crash it also fixes: `confirm_clean` assumed a parsed manifest was an object and raised `AttributeError` on a JSON array, and since `check` does not wrap the call, a clean fixture with an array manifest would have aborted the whole oracle run with a traceback instead of reporting a refusal. `check:fixtures` gains a hash-coherence pass over every `{path, hash}` pair a document fixture's manifest DECLARES — content part, asset index, presentation layer and extension config slot alike, 143 hashes across 123 fixtures: each must agree with the bytes the recipe stores, and must DISAGREE exactly where the case expects the mismatch code for that reference's class. This cannot live in `check:conformance` — the fixture comparator is a subset check, so an unexpected hash-mismatch finding is tolerated outright, and on a case already expecting a WARNING or a REJECT it cannot move the document disposition either. Measured on `reject-content-key-non-nfc`: flipping one hex digit of its content hash leaves all 366 conformance checks green while the new gate names it. The claim is scoped deliberately — on the five cases expecting exactly [IGNORE, IGNORE] the extra WARNING DOES move the disposition and `check:conformance` catches it, so the hole closed is the WARNING and REJECT population, not literally every non-clean fixture. Scope beyond `content.hash` was not optional: corrupting one non-clean fixture's asset-index hash was measured invisible to `check:conformance`, `check:fixtures`, `check:document-oracle` and `check:document-id` together. The pass declines a digest this runtime cannot compute rather than throwing — blake3 is permitted by Container §3.2 and declared in `capabilities.json`, and an uncaught throw there aborted the gate and took both independent oracles with it — and it pins BOTH its skip sets by NAME — the fixtures carrying no comparable reference, and the individual references it declined — with a floor on what was compared, because a gate that reports a tick having compared nothing, or that folds an unverified hash into the count of those that agree, is the same silent pass it exists to remove. `manifest.security.accessControl` is carried deliberately with NO code: it is the one security-block reference declared as a `{path, hash}` rather than a bare path and nothing in the reader verifies its hash, so the pass still requires it to match its bytes but does not attribute a disagreement to a code no implementation emits — which would make such a fixture unauthorable. The boundary is stated with what it leaves out rather than only what it covers: an asset whose bytes diverge from the hash listed INSIDE an index file is pinned by the oracle's asset arms on clean fixtures only, so it remains unpinned on a non-clean one, which is this same hole one level down. One document fixture (157 fixtures, 366 checks), `reject-metadata-term-non-nfc-array-element` is the coverage one: §4.3.1 keeps exactly five Dublin Core terms and projects `creator`, `subject` and `language` as ARRAYS, a scalar being coerced to a one-element array, while the AUTHORED value may be either shape — and every other Dublin Core part in the corpus authors the scalar, so no case had the array shape reaching §4.3.2's scan. Verified against both implementations separately: dropping the array terms from the reference's loop fails it on the document DISPOSITION, and dropping them from the oracle's makes it unable to confirm the defect. Four `test-document-verdict` cases for what the corpus cannot express: the array shape at the verdict layer for each of the three array-valued terms — pinning only `creator` was measured to leave `subject` and `language` unscanned in BOTH implementations with the entire corpus green — and the negative control for the concatenation scan's run flush. `reject-content-split-combining-sequence-mid-array` pins that a run IS reported at a non-text element but not that the flush SEPARATES; the control is a PAIR carrying the same four text-node values inside a `blockquote`, differing only by a paragraph between the second and third, each run NFC-stable alone and only their concatenation not. - Conformance defect vocabulary `conformance/errors.json` **v0.14**: eight new codes for content-part validity. `CDX-E-CONTENT-ROOT-MALFORMED` (REJECT), `CDX-E-PART-STRING-NOT-NFC` and `CDX-E-PART-STRING-ILL-FORMED` (REJECT, both citing §5.4.3 as their siblings do), `CDX-E-ANNOTATION-ANCHOR-POSITION-INVALID` (WARNING, state-invariant), `CDX-E-ANCHOR-POSITION-INVALID` with **`disposition: null`** — §7.2's severity table covers only three anchor conditions and a structurally invalid position is none of them, so the gap is recorded rather than filled by analogy, and joins OQ-007's register — and **three** out-of-range codes rather than one, because an out-of-range position is disposed of by the §5.4.2 row of the FIELD carrying it and those rows do not agree. `CDX-E-ANCHOR-POSITION-OUT-OF-RANGE` is scoped to a `link` href, taking the dangling-core-anchor row, whose cited Anchors and References §7.2 tabulates exactly this condition and escalates it when frozen; `CDX-E-BLOCK-REFERENCE-POSITION-OUT-OF-RANGE` takes the extension-block-field row and inherits `CDX-E-BLOCK-REFERENCE-DANGLING`'s recorded contest; `CDX-E-CROSS-REFERENCE-POSITION-OUT-OF-RANGE` takes the extension-cross-reference row, WARNING in every state. One code across all three would publish a single disposition for rows that diverge, and post-B3 an `academic:theorem-ref` whose target was MISSING would stay a WARNING while one naming a merely stale offset became an INTEGRITY-ERROR. The vocabulary is append-only, so the arms had to be separated before a disposition was published, not after; the §7.2-versus-§5.4.2 conflict the cross-reference code records is new **OQ-011**, settled by neither. The structural arm is deliberately NOT split — a null disposition contributes nothing to a verdict and so cannot diverge between rows. The two Unicode codes are scanned over the part's **hashed material** — the stored bytes minus the fields canonicalization deletes — matching the "a **hashed** object key or string value" both rows and both summaries bind. A violation inside a deleted field (`crdt`, `codeBlock.tokens`, `measurement.display`) is therefore NOT reported: it is not hashed, and the split-view harm cannot reach it, since two readers cannot derive different canonical bytes from a field both delete. `positive-content-derived-field-non-nfc` is the published control for that boundary — a reader scanning the whole stored part rejects a conformant document in every state, and `crdt` carries opaque third-party state holding arbitrary user text. A field the transform *rewrites* rather than deletes IS reported, an asset path being replaced before validation runs. The third arm of the same clause, `CDX-E-PART-NUMBER-NON-REPRESENTABLE`, stays raw-scoped and so does not match: it was published that way, and narrowing it would flip an expectation an implementation may already meet. Twenty-nine document fixtures (156 total), two new `anchor-range` structural vectors (209 published vectors), independent Python confirmers for each new code a fixture can assert (seven of the eight; `CDX-E-ANCHOR-POSITION-INVALID` has none, having nothing to confirm) plus the matching `confirm_clean` arms, and forty `test-document-verdict` cases for the properties a fixture cannot express — the comparator requires every expected finding to carry a disposition interval, so no fixture can assert a null-disposition code, and being a subset check it cannot assert that a defect reported under one row is NOT also reported under another. Two of those fixtures pin properties of the position check that a single-text-node target cannot express: a range whose bounds are DISTINCT integers above 2^53, ordered by comparing the digit strings rather than the doubles they round to (`contentAnchorUri` admits an unbounded `[0-9]+`, and §4.3.2's 2^53 limit governs hashed *numbers*, not digits inside a string — so a double comparison finds the bounds equal and silently downgrades a tabulated WARNING to the null-disposition structural code); and a target whose text spans two text nodes, which is what makes §3's concatenation model observable at all — `join('')` to `join(' ')` previously survived in the reference AND the oracle, a shared misreading no gate could see. The derived text-bearing vocabulary is now pinned by assertion rather than only by the throw-on-empty guard, which measurement showed was not enough on its own: dropping `figcaption` from the derived set leaves the entire corpus green — every conformance check and every oracle confirmation — because no fixture anchors into one and a wrong set only produces the null-disposition structural code, which is invisible in both of the comparator's dimensions. The pin is written against the SPECIFICATION rather than against the derivation's output, which is what caught the next defect: `codeBlock` was MISSING from the derived set, because its schema reaches `textNode` through an `allOf` that narrows it (§4: exactly one marks-free text node) rather than through a direct reference. §3 names `codeBlock` text-bearing outright, so an anchor into a code block — the ordinary reason to anchor at all — was reported as targeting a non-text-bearing block on conformant content, and an out-of-bounds one was downgraded from the tabulated WARNING to the null-disposition code. The pin asserts two ONE-SIDED relations rather than an equality, which is the form §3 actually supports: it names its five types with "such as", so the list is illustrative and the definition is the children test. An equality assertion would fail on a CORRECT widening, and the cheapest route back to green from that failure is to narrow the derivation again — re-creating the defect. The lower bound is that every type §3 names is derived; the upper bound is that no container block is, §3 being explicit that a container "has no text content of its own". `conformance/suite.json` `suiteVersion` 0.2.1 -> 0.2.2, and its `versioning.rules` gains the rule both patch releases to date — 0.2.1 and this one — have followed: while pre-1.0 the minor position carries the breaking bump, so added cases and newly reported defect classes land in patch, which means a pre-1.0 patch bump CAN add an expectation an implementation is held to. v0.13's entry below stated it in prose; what it had never been given was a rule in the normative artefact. `conformance/capabilities.json` 0.2.0 -> 0.2.1, its `document` summary having claimed block/mark structure, NFC and the hash recomputes all still rode with a later phase, two of which had been false since B1b-2 and B1b-3a

### Fixed
- **An `id` carried under `attributes` is no longer relabeled, closing a silent document-ID collision.** §4.3.1 item 5 relabels author-chosen identifiers so two documents differing only in their LABELS share an id. That alpha-equivalence was reaching third-party vocabulary data, where an id is content: measured, two bibliographies whose CSL citation keys differed entirely — `smith2020`/`jones2019` versus `OTHER-KEY`/`DIFFERENT` — canonicalized to identical bytes, so **a signature over one verified the other**. Whether it fired turned on `type` versus `@type`, leaving well-formed JSON-LD accidentally immune and CSL-JSON exposed — the shape test leaking, where item 5 says membership is keyed on position. Item 5 already exempts a `semantic:bibliography` entry's `id` for exactly this reason; the same data one field over was not. **PRESERVED, not excluded**, and the distinction is the whole fix: excluding takes the id out of the namespace but leaves `rewriteIds` mapping it onto a generated name, which trades a loud failure for a silent one — that approach was implemented and reverted on the previous branch. A preserved id stays in the map's INPUT and out of the map, so `renameId` returns it verbatim, reusing the mechanism `semantic:term` and `semantic:footnote` already use, and inheriting item 5's canonical-name prohibition for free. **The duplicate cases still REJECT, and that is correct.** The premise that nothing can reference material under `attributes` is false as implemented: a `link` mark's `href` resolves into it and is rewritten, so a duplicate id there leaves a reference with two candidate referents. The code comment asserting “nothing anchors into it” stated a wish as a fact. One consequence is deliberate: a preserved occurrence **consumes no index**, so a real sibling block now takes the name the preserved one would have had, changing the document id of any document carrying an id under `attributes`. Item 5 states that rule and records that reserving an index instead “would give identical content a different document ID”. Zero documents in the corpus carry one, measured. The remaining consumers of the barrier — the reference resolver's walks, and the structural id-uniqueness check — are unchanged and tracked separately; this closes the collision, not the whole barrier question.
- **Conformance suite `suiteVersion` 0.2.4 → 0.2.5.** 215 → 216 vectors, 163 → 164 fixtures, 378 → 380 checks. The vector and the fixture kill DIFFERENT mutants and both are needed: relabeling returning is caught only by the vector (`"id":"smith2020"` versus `"id":"b0"`), while excluding ids from the namespace rather than preserving them is caught only by the fixture (disposition IGNORE where INTEGRITY-ERROR is required). Nothing in the published suite caught that second case before, which is how the reverted approach reached a branch. The fixture expects a disposition RANGE rather than a pin, since `CDX-E-ID-COLLISION` is registered INTEGRITY-ERROR and the later states escalate it. The Python oracle needs no counterpart — measured, not assumed: it does not relabel, so preserved-versus-relabeled is invisible to it, and it confirms the new fixture independently.
- **Canonicalization no longer REJECTs conformant documents carrying text-shaped data in a position that is not block content.** Document Hashing §4.3.1 item 4 (merge adjacent text nodes) and §4.3.2 item 2 (concatenated-NFC) were implemented on element **shape** — “is this object `{type:"text",value:string}`?” — so ANY array whose members merely resembled text nodes was merged and run-checked. Both rules are now keyed on **position**: the schema-declared block-content arrays `blocks`, `caption`, `children`, `content`, `hints`, `preamble`, plus `attributes` as a **sticky** barrier. The barrier is what the shape reading gets wrong in practice: `attributes.semantic` is a JSON-LD annotation with `additionalProperties: true` (semantic.schema.json), so an author may put a member named `children` there at any depth, and clearing the flag on the way down readmits the very false REJECT the scoping removes. Only the RUN rule is withheld beneath `attributes` — it is HASHED material, so both **per-string** invariants still bind there, pinned by two REJECT fixtures; without them the scope could be widened into a wholesale exemption with every gate green, only a non-NFC KEY having been covered. The set is **keys, not (type, key) pairs**, because several content arrays hang off sub-objects carrying no `type` at all (`exercisePart`, `solution`, a phantom's content), which a type-keyed map cannot reach. **The scope is a NARROWING, and its licence is not yet in `spec/`.** §4.3 applies the transforms across all block types “uniformly” and §4.3.2 binds the rule to “a block” with no enclosing-field list, where §4.3.1 item 5 names `lines`/`subfigures` as exhaustive when it means to scope by position. Measured: a `vendor:callout` carrying `body:[text,text]` with a split combining sequence REJECTed before and loads clean now. A spec erratum is required and is tracked separately; until it lands the reference under-enforces §4.3.2 for extension blocks whose text array is not one of the six keys. Strict `children` is the specific wrong answer, and it is measurable: it drops the ROOT `blocks` array that `reject-content-split-combining-sequence-mid-array` uses AND `figure.caption`, and now breaks **eight** published cases (four vectors, four fixtures) where before this slice it broke one. **Six walks** were scoped, four in `scripts/lib/canonicalize.ts` (`canon`, `walkContentNodes`, `validateStoredByteInvariants`, `collectStoredTextViolations`) and two in `conformance/oracles/document_oracle.py` (`_walk_text_violations`, `_walk_content`). `dropAbsorbedTextNodes` and `_drop_absorbed_text_nodes` — the pair an earlier withdrawn attempt missed — are unchanged in body; what was scoped is their INVOCATION, inside `walkContentNodes` and `_walk_content` respectively. Those two model the merge for the RAW walk, and scoping the other four alone makes canon keep a node the raw walks drop. **The barrier gates the merge and the run rule, NOT id-namespace membership**, and that asymmetry is deliberate for now rather than settled. `definedId` still counts an id carried under `attributes`, so two `anchor` marks sharing one there is a REJECT even though the merge treats the same subtree as inert. Gating `definedId` as well was implemented and REVERTED: it removes ids from the namespace but `rewriteIds` still relabels them, so two documents differing only in an id under `attributes` canonicalized to identical bytes — a silent document-ID collision in place of a loud false REJECT, which is the worse trade in a content-addressed format. The barrier has to reach `definedId`, `rewriteIds` and the reference resolver together or not at all; that is tracked separately. **Scan and canon agree at every position they both reach, with one KNOWN divergence.** `canon` skips a text node's `marks`, and `content` (a `presentation:footnote` mark's content blocks) occurs only there, so at that position the run rule fires and the merge does not — split text in a footnote mark's content is reported, while two mark-less nodes there stay unmerged. That asymmetry is #121's sequel, not a licence to widen the scope, and it is stated in the published vector rather than left for an implementer to infer. `check:block-content-positions` re-derives the set from the published schemas and fails on drift, comparing each transcription against the SCHEMA rather than against the other. Its derivation is **recursive and resolves local `$ref`s**: a position declared behind a `$ref` to an array-typed `$def`, or on an inline nested object (the shape `academic:abstractBlock.sections[].children` already uses), was previously invisible — and under-derivation is the one failure the gate cannot report on itself, since a key it never saw is a key both sets agree about. Both shapes now fail it. It also compares `CONTENT_BARRIER_KEY` across the two implementations and against `blockBase`, which nothing checked before. The change is a pure relaxation with **zero id blast radius** in this repository: every id-verifying gate passes unchanged and no example or fixture exercised the path.
- **The published `anchor-range` structural rule no longer false-positives on a well-ordered range above 2^53.** `checkAnchors` ordered a Content Anchor URI's bounds by converting them to numbers, so two distinct integers that round to the same double compared equal and the range was reported inverted — under a message naming the same number twice. The URI grammar admits an unbounded `[0-9]+` and §4.3.2's 2^53 limit governs hashed *numbers* rather than digits inside a string, so such a URI is conformant. This mattered beyond its own rule: the document layer's position check had the identical defect and was fixed in the same change, which left two implementations in this repo disagreeing about the exact URI a new fixture pins. The comparison is now shared between them (`scripts/lib/decimal-digits.ts`), which is also what forced the leading-zero case to be handled — `[0-9]+` admits `007`, so a length-first digit comparison would otherwise have called `#p1/007-10` inverted. Two `anchor-range` vectors pin both
- Broken cross-reference in presentation layers spec (Section 5.1.2 → 5.4)
- Sync checker false positives for MIME types, token types, and enum values

### Changed
- **Specification errata (two defect classes given dispositions, closing two of State Machine §5.4.2's silent gaps).** Both are **normative TIGHTENINGS**: a document that loaded before now REJECTs. (1) The **stored-byte Unicode invariants** of Document Hashing §4.3.2 item 2 — NFC and well-formed Unicode — gain two §5.4.2 rows and a §5.4.3 state-invariant bullet, joining the two siblings of the same clause (duplicate keys, non-representable numbers) that already REJECT in every state. Item 2 stated no consumer REJECT obligation — it already bound producers to emit NFC and implementations not to normalize at hash time, and called non-NFC content non-conformant, but never said what a verifier does with such a document — so it gains the consumer sentence item 1 already carries; without it the §5.4.3 bullet would have no mechanism clause to defer to. Two rows rather than one, because the harms differ and the table partitions by justification: an unpaired surrogate has no UTF-8 encoding at all, so RFC 8259 parsers diverge and two conformant readers derive different document IDs from one archive; non-NFC content hashes deterministically but leaves the ADDRESSING layer split, since Anchors and References §3 defines character offsets over NFC text. **What this changes in practice:** a decomposed (NFD) string — routine on macOS, and emitted by several IME pipelines — previously loaded silently, with the canonicalization throw swallowed by the document-ID recompute's catch and `manifest.id` left unverified; it is now a REJECT in every state. Content Blocks §6.2's "Implementations MUST support: All Unicode normalization forms" is qualified in the same erratum, since read literally it obliged a reader to accept the content §4.3.2 forbids. (2) The **content root envelope** (Content Blocks §2.2) gains a §5.4.2 row and a §7.1 structural rule: a content part that parses but is not an object, or whose `version` or `blocks` is absent or of the wrong JSON type, REJECTs. The mistyped-`blocks` arm is the one that matters — every content-level row in the §5.4.2 table is reached by walking `blocks`, so a non-array withdraws all of them at once while the document id stays computable and a signature over it still verifies, which two independent implementations both demonstrated. The root stays OPEN (no `additionalProperties`), and a value-invalid `version` such as `"0.1.0"` is deliberately left unreported: §5.4.2 assigns it no row, and its version rows govern the manifest `cdx` field rather than the content model. §5.4's preamble gains Content Blocks, absent from it until now
- **Footnote marks are now resolved**, taking State Machine §5.4.2's extension-cross-reference row from three covered arms to four. Semantic Extension §4.5.2 is implemented as written: a `footnote` mark resolves to its `semantic:footnote` block by `id` when both carry one (id match taking precedence), otherwise by its `number` or `symbol` marker. Two codes, because the failures are different — `CDX-E-FOOTNOTE-REFERENCE-DANGLING` when nothing matches, and `CDX-E-FOOTNOTE-REFERENCE-AMBIGUOUS` when a marker matches more than one block, which §4.5.2 makes a WARNING while sending the reader to the first block in document order. The namespace is purely in-document, so unlike the citation and glossary arms it has no side file and therefore no indeterminate case. One reading is recorded rather than settled: where a mark carries an `id` matching no block, this implementation falls back to the marker instead of reporting immediately — §4.5.2's “resolves … by a single key” supports the strict reading at least as well — arguably better, since it is the only reading under which the section's MUST can be violated at all. The choice constrains nobody else: no published fixture or vector carries the disputed shape, and the comparator is a subset check, so a reader implementing the strict reading still passes the corpus. The divergence is warn-vs-silent, not WARNING-vs-WARNING
- **A `semantic:term` and a `semantic:footnote` block's `id` is left as authored** through canonicalization (Document Hashing §4.3.1 item 5; DD-022). Both blocks are the *defining* side of a reference that addresses a separate namespace and is itself never relabeled — a `glossary` mark's `ref` and a `semantic:term` `see` resolve against a term block's `id` (Semantic Extension §8.3 rule 2), a `footnote` mark against a `semantic:footnote` block (§4.5.2) — so relabeling only the definition left both rules unsatisfiable on the canonical form: the block became `b0` while the reference still named `term-algorithm`. Item 5's previous text asserted the opposite ("still has its own block `id` relabeled like any other block id") and is corrected. **Membership is unchanged**: a preserved id remains in the shared uniqueness-and-anchor namespace, a duplicate is still a canonicalization error, and a Content Anchor URI still resolves against it — only the renaming skips it, which is why §8.3 rule 2 and §4.5.2 needed no rewording. Two consequences are stated normatively rather than left implicit: a preserved id MUST NOT itself spell a canonical name (`b` followed by digits), because duplicate detection compares *authored* ids and so cannot see an authored `b0` colliding with a generated one; and the `b<n>` sequence **compacts** over a preserved occurrence rather than reserving an index, since reserving is equally implementable and would give identical content a different document ID. This **changes the document ID** of any document carrying a term or footnote block id, including two committed examples. Membership in the exception is keyed on block `type`, departing from item 5's "keyed on WHERE an id sits" principle of necessity — a term block's id sits exactly where any other block id does
- **Mark re-sorting is now scoped to a text node's `marks`, matching §4.3.1 item 3.** Item 3 is stated "within each text node" and the canonical transform normalizes marks under the text-node case alone, but the identifier-rewriting pass re-sorted and de-duplicated *every* array named `marks`, wherever it sat. A JSON-LD block annotation and a CSL bibliography entry both admit arbitrary members, so a `marks` array carried inside one was being normalized although the canonical form never touches it — two documents differing only in that array's order collapsed onto a single document ID. Found while closing the early-return hole below, which made the mis-scoped pass reachable for documents that define no ids and so exposed it generally
- **An unresolved `#b<digits>` reference is now rejected in a document that defines no ids at all.** §4.3.1 item 5 has always made such a reference a canonicalization error unconditionally, but the reference implementation returned early when the identifier namespace was empty, so the rewriting pass — which enforces the prohibition — never ran: a dangling `#b0` was accepted in a document with no ids and rejected in the same document with one id added. A document carrying only preserved ids takes the same path, so the fix precedes the change above rather than following it
- **Specification errata (five decisions transcribed into normative text).** Each closes a place where the conformance suite had to record a *reading* because §5.4.2 assigned no row or the specification contradicted itself. (1) **Absent metadata is a manifest defect, not a metadata defect** — §5.4.2's metadata row is now explicitly PART-level (a Dublin Core part referenced but absent or unparseable, or a missing required term), and an absent or mistyped `metadata`/`metadata.dublinCore` *field* falls under the manifest row instead. This is a normative TIGHTENING: a manifest declaring no `metadata` previously loaded with a warning and is now REJECT, which is what the schema always implied, `metadata` being required and `dublinCore` required within it. (2) **The out-of-hash extension-data row's examples corrected** — a semantic bibliography or glossary and an academic numbering configuration are declared as `{path, hash}` pairs that the manifest projection binds, so they were never "path-only" and the row's own qualifier excluded them; the hash-bound row governs, making them INTEGRITY-ERROR when frozen rather than WARNING. That row keeps genuinely path-only data such as `metadata.jsonld`. The HASH-BOUND row correspondingly gains "or unparseable" (excluding the `content` part, which its own row rejects, and the unobtainable-bytes cases of notes 5 and 6), so a projection-bound side file that is present but will not parse is not stranded between the two. The academic extension's own integrity note, which asserted the opposite disposition for `numbering.json`, is corrected to match. (3) **A declared asset-index path that diverges from the derived location is now REJECT** — Asset Embedding §3.1 stated the equality as a MUST and then resolved a disagreement leniently ("the derived path governs"); that sentence is deleted and §5.4.2 gains a REJECT row, because a divergence leaves the document ambiguous — a reader honouring the declaration and one honouring the derivation resolve the category's assets differently — and splits identity from attestation, the projection binding the declared path's hash while the document ID inherits the asset hashes listed in the file at the derived path. No projected bytes change: for every loadable document the two paths name one file. The row states the comparison rule (§4.3.1 path normalization) so "does not equal" is not left to the reader. (4) **`flowElement.blockIds` named** — Presentation Layers §13.4 and the dangling-presentation-reference row enumerated only `blockId` and `blockRefs`, though a flow element's `blockIds` references content blocks identically (§6.4). §13.4 now names all three and scopes the completeness claim to fields *within a presentation-layer or precise-layout file*, since a `presentation:reference` block's `target` also addresses a content block but lives in the content tree rather than a presentation file (which row disposes of a dangling one is a separate question the erratum does not settle); the `blockId` parenthetical also picks up `preciseElement` (§12.3), which is a different type from `pageElement`. No behavioural change. (5) **A dedicated §5.4.2 row for an undeclared presentation or precise-layout file** — WARNING in draft/review, INTEGRITY-ERROR when frozen or published, replacing a disposition previously inferred from the §5.4.2 preamble and Presentation Layers §12. The row states the membership test the disposition turns on (a precise layout carries `presentationType`, a reactive presentation a `type` of `paginated`, `continuous`, or `responsive`; any other file under `presentation/` stays IGNORE) and the unrecognized-file row is carved out to match, so the two no longer both reach one artifact. A second normative TIGHTENING: §12's "SHOULD be surfaced as an integrity concern" becomes a MUST, since an INTEGRITY-ERROR obliges a reader to surface the failure (§5.4.1) and a SHOULD cannot support that; §12 also now states that an undeclared *reactive* presentation file is covered, which it previously left to the §5.4.2 preamble alone
- Container Format §3.2's compression-method table is now stated to be the **complete permitted set**, and a reader MUST NOT infer a method from the data (in particular MUST NOT treat an unrecognized method as Deflate). This is a normative NARROWING: "MAY use the following" granted permission for those three methods without by itself forbidding others, and §3.1's APPNOTE.TXT conformance defines BZIP2, LZMA, XZ and PPMd — so an archive using one of those was arguably conformant and now is not. Two new State Machine §5.4.2 rows dispose of the closed set (a forbidden method, and an entry that will not decode under a permitted one — both REJECT), and a new note 6 covers the opposite case: an entry using a PERMITTED method the reader has not implemented (Zstandard is RECOMMENDED, not required) is not a defect, is reported integrity-indeterminate, and MUST NOT fire the missing-part rows — mirroring note 5 for encrypted parts, including its document-level conclusion where the entry carries required or hash-bound content. §5.4.1 gains a paragraph stating that integrity-indeterminate is not one of the four dispositions. Motivated by a reference-reader defect: treating every non-Store method as Deflate meant a Zstandard entry threw, the throw was swallowed, and the archive reported clean with its CRC-32 and every hash over those bytes unverified
- Content schema now references legal extension marks (`legal:cite`)
