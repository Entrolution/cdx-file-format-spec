# Changelog

All notable changes to the CDX file format specification.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [0.1] - 2025-01 (Draft)

### Added

#### Core Specification
- Security Model document (spec/core/11-security-model.md): consolidated attacker model, guarantees/non-guarantees inventory, the lifecycle-downgrade reduction in context, an informative mapping of the published PDF signature attack classes (ISA/SWA/USF, shadow attacks, certification attacks) onto CDX mechanisms and residuals, a verifier-obligations index (the scoping brief for external review), and a disclosure index locating every accepted-limitation statement
- Document manifest with state machine (draft → review → frozen → published)
- Content block model with 22 block types
- Dublin Core metadata support
- Asset embedding and management
- Provenance and lineage tracking
- Anchors and references system
- Presentation layers (paginated, continuous, responsive, precise)
- Highlight annotation documentation in collaboration extension (Section 4.7)

- **Collaboration** (`cdx.collaboration` v0.2) - CRDT integration, comments, change tracking, presence

- **Legal** (`cdx.legal`) - Citations, Table of Authorities, court captions, signature blocks
- **Phantoms** (`cdx.phantoms`) - Off-page annotation layer for spatially-organized content (research notes, marginalia, mind-maps)
- **Presentation** (`cdx.presentation`) - Advanced typography, master pages, print features
- **Security** (`cdx.security`) - Digital signatures, encryption, redaction, scoped signatures
- **Semantic** (`cdx.semantic`) - Bibliography, footnotes, glossary, entity markup, JSON-LD

#### Tooling
- Conformance defect vocabulary `conformance/errors.json` **v0.14**: eight new codes for content-part validity. `CDX-E-CONTENT-ROOT-MALFORMED` (REJECT), `CDX-E-PART-STRING-NOT-NFC` and `CDX-E-PART-STRING-ILL-FORMED` (REJECT, both citing §5.4.3 as their siblings do), `CDX-E-ANNOTATION-ANCHOR-POSITION-INVALID` (WARNING, state-invariant), `CDX-E-ANCHOR-POSITION-INVALID` with **`disposition: null`** — §7.2's severity table covers only three anchor conditions and a structurally invalid position is none of them, so the gap is recorded rather than filled by analogy, and joins OQ-007's register — and **three** out-of-range codes rather than one, because an out-of-range position is disposed of by the §5.4.2 row of the FIELD carrying it and those rows do not agree. `CDX-E-ANCHOR-POSITION-OUT-OF-RANGE` is scoped to a `link` href, taking the dangling-core-anchor row, whose cited Anchors and References §7.2 tabulates exactly this condition and escalates it when frozen; `CDX-E-BLOCK-REFERENCE-POSITION-OUT-OF-RANGE` takes the extension-block-field row and inherits `CDX-E-BLOCK-REFERENCE-DANGLING`'s recorded contest; `CDX-E-CROSS-REFERENCE-POSITION-OUT-OF-RANGE` takes the extension-cross-reference row, WARNING in every state. One code across all three would publish a single disposition for rows that diverge, and post-B3 an `academic:theorem-ref` whose target was MISSING would stay a WARNING while one naming a merely stale offset became an INTEGRITY-ERROR. The vocabulary is append-only, so the arms had to be separated before a disposition was published, not after; the §7.2-versus-§5.4.2 conflict the cross-reference code records is new **OQ-011**, settled by neither. The structural arm is deliberately NOT split — a null disposition contributes nothing to a verdict and so cannot diverge between rows. The two Unicode codes are scanned over the part's **hashed material** — the stored bytes minus the fields canonicalization deletes — matching the "a **hashed** object key or string value" both rows and both summaries bind. A violation inside a deleted field (`crdt`, `codeBlock.tokens`, `measurement.display`) is therefore NOT reported: it is not hashed, and the split-view harm cannot reach it, since two readers cannot derive different canonical bytes from a field both delete. `positive-content-derived-field-non-nfc` is the published control for that boundary — a reader scanning the whole stored part rejects a conformant document in every state, and `crdt` carries opaque third-party state holding arbitrary user text. A field the transform *rewrites* rather than deletes IS reported, an asset path being replaced before validation runs. The third arm of the same clause, `CDX-E-PART-NUMBER-NON-REPRESENTABLE`, stays raw-scoped and so does not match: it was published that way, and narrowing it would flip an expectation an implementation may already meet. Twenty-nine document fixtures (156 total), two new `anchor-range` structural vectors (209 published vectors), independent Python confirmers for each new code a fixture can assert (seven of the eight; `CDX-E-ANCHOR-POSITION-INVALID` has none, having nothing to confirm) plus the matching `confirm_clean` arms, and forty `test-document-verdict` cases for the properties a fixture cannot express — the comparator requires every expected finding to carry a disposition interval, so no fixture can assert a null-disposition code, and being a subset check it cannot assert that a defect reported under one row is NOT also reported under another. Two of those fixtures pin properties of the position check that a single-text-node target cannot express: a range whose bounds are DISTINCT integers above 2^53, ordered by comparing the digit strings rather than the doubles they round to (`contentAnchorUri` admits an unbounded `[0-9]+`, and §4.3.2's 2^53 limit governs hashed *numbers*, not digits inside a string — so a double comparison finds the bounds equal and silently downgrades a tabulated WARNING to the null-disposition structural code); and a target whose text spans two text nodes, which is what makes §3's concatenation model observable at all — `join('')` to `join(' ')` previously survived in the reference AND the oracle, a shared misreading no gate could see. The derived text-bearing vocabulary is now pinned by assertion rather than only by the throw-on-empty guard, which measurement showed was not enough on its own: dropping `figcaption` from the derived set leaves the entire corpus green — every conformance check and every oracle confirmation — because no fixture anchors into one and a wrong set only produces the null-disposition structural code, which is invisible in both of the comparator's dimensions. The pin is written against the SPECIFICATION rather than against the derivation's output, which is what caught the next defect: `codeBlock` was MISSING from the derived set, because its schema reaches `textNode` through an `allOf` that narrows it (§4: exactly one marks-free text node) rather than through a direct reference. §3 names `codeBlock` text-bearing outright, so an anchor into a code block — the ordinary reason to anchor at all — was reported as targeting a non-text-bearing block on conformant content, and an out-of-bounds one was downgraded from the tabulated WARNING to the null-disposition code. The pin asserts two ONE-SIDED relations rather than an equality, which is the form §3 actually supports: it names its five types with "such as", so the list is illustrative and the definition is the children test. An equality assertion would fail on a CORRECT widening, and the cheapest route back to green from that failure is to narrow the derivation again — re-creating the defect. The lower bound is that every type §3 names is derived; the upper bound is that no container block is, §3 being explicit that a container "has no text content of its own". `conformance/suite.json` `suiteVersion` 0.2.1 -> 0.2.2, and its `versioning.rules` gains the rule both patch releases to date — 0.2.1 and this one — have followed: while pre-1.0 the minor position carries the breaking bump, so added cases and newly reported defect classes land in patch, which means a pre-1.0 patch bump CAN add an expectation an implementation is held to. v0.13's entry below stated it in prose; what it had never been given was a rule in the normative artefact. `conformance/capabilities.json` 0.2.0 -> 0.2.1, its `document` summary having claimed block/mark structure, NFC and the hash recomputes all still rode with a later phase, two of which had been false since B1b-2 and B1b-3a
- Conformance defect vocabulary `conformance/errors.json` **v0.13**: two new codes for the footnote arm — `CDX-E-FOOTNOTE-REFERENCE-DANGLING` and `CDX-E-FOOTNOTE-REFERENCE-AMBIGUOUS`, both WARNING. The dangling code's disposition is transcribed from §5.4.2's extension-cross-reference row, which already named the footnote mark, and §4.5.2 restates it. The ambiguous one is weaker and the vocabulary says so: §5.4.2 assigns the ambiguity case no row at all, and §4.5.2 states the WARNING without a state qualifier and without citing §5.4 — so unlike its three siblings that entry does not claim state-invariance, and neither does this line. `CDX-E-CROSS-REFERENCE-DANGLING`'s "COVERAGE IS PARTIAL" note is rewritten: four of the row's five arms now have codes — citation, glossary, footnote, and the three `academic:*-ref` marks that code itself covers. The LEGAL arm remains uncovered, and the note now says so rather than passing over it: Legal Extension §5 states the disposition for a `legal:cite` whose `category` matches no Table of Authorities category, but it matches against a configuration rather than a content namespace, so it needs its own collector and its own answer on whether an absent configuration is indeterminate. Three document fixtures (127 total) and an independent Python confirmer that counts blocks per marker, since a flat id set cannot tell an ambiguous marker from a dangling one; `conformance/suite.json` `suiteVersion` 0.2.0 -> 0.2.1, the patch position being where added cases land now that the minor position carries the pre-1.0 breaking bump
- Conformance defect vocabulary `conformance/errors.json` **v0.12**: `CDX-E-ID-COLLISION`'s note re-synced — it asserted the shared namespace "is exactly the one Document Hashing §4.3.1 item 5 relabels", which the preserved-id erratum makes false; the namespace is now a superset of what item 5 relabels, and the note distinguishes a `semantic:footnote` BLOCK id (a member) from the footnote MARK id that resolves to it (a separate namespace). `CDX-E-GLOSSARY-REFERENCE-DANGLING`'s recorded "specification tension" is retracted as resolved. Six `canonicalize` vectors added and one flipped (207 published vectors), covering the preserved id, the matching glossary `ref`, index compaction, and the three new rejects. `conformance/suite.json` `suiteVersion` 0.1.0 -> 0.2.0: the flipped vector replaces a published `expectedCanonicalJcs` and `expectedId`, which the suite's own rule calls a changed expectation (the breaking bump sits in the minor position while the suite is pre-1.0)
- Conformance defect vocabulary `conformance/errors.json` **v0.11**: new code `CDX-E-MANIFEST-FIELD-MISSING` (REJECT) for an absent required manifest field, taking the no-`metadata`-reference arm that `CDX-E-METADATA-PART-MISSING` previously carried at WARNING; `CDX-E-ASSET-INDEX-PATH-DIVERGENT` moves from `disposition: null` to REJECT now that §5.4.2 assigns it a row. The `compatibilityPolicy` gains four rules stating what a specification erratum may change in a published entry — `clause`/`dispositionClause` re-synced to amended text, a null disposition made concrete when the gap closes, a `summary` narrowed (never widened) when one of its arms moves to a new code, and rows cited by quoting them rather than by number. A concrete disposition still never becomes a different concrete disposition

### Fixed
- **The published `anchor-range` structural rule no longer false-positives on a well-ordered range above 2^53.** `checkAnchors` ordered a Content Anchor URI's bounds by converting them to numbers, so two distinct integers that round to the same double compared equal and the range was reported inverted — under a message naming the same number twice. The URI grammar admits an unbounded `[0-9]+` and §4.3.2's 2^53 limit governs hashed *numbers* rather than digits inside a string, so such a URI is conformant. This mattered beyond its own rule: the document layer's position check had the identical defect and was fixed in the same change, which left two implementations in this repo disagreeing about the exact URI a new fixture pins. The comparison is now shared between them (`scripts/lib/decimal-digits.ts`), which is also what forced the leading-zero case to be handled — `[0-9]+` admits `007`, so a length-first digit comparison would otherwise have called `#p1/007-10` inverted. Two `anchor-range` vectors pin both
- Broken cross-reference in presentation layers spec (Section 5.1.2 → 5.4)
- Sync checker false positives for MIME types, token types, and enum values

### Changed
- **Specification errata (two defect classes given dispositions, closing two of State Machine §5.4.2's silent gaps).** Both are **normative TIGHTENINGS**: a document that loaded before now REJECTs. (1) The **stored-byte Unicode invariants** of Document Hashing §4.3.2 item 2 — NFC and well-formed Unicode — gain two §5.4.2 rows and a §5.4.3 state-invariant bullet, joining the two siblings of the same clause (duplicate keys, non-representable numbers) that already REJECT in every state. Item 2 stated no consumer REJECT obligation — it already bound producers to emit NFC and implementations not to normalize at hash time, and called non-NFC content non-conformant, but never said what a verifier does with such a document — so it gains the consumer sentence item 1 already carries; without it the §5.4.3 bullet would have no mechanism clause to defer to. Two rows rather than one, because the harms differ and the table partitions by justification: an unpaired surrogate has no UTF-8 encoding at all, so RFC 8259 parsers diverge and two conformant readers derive different document IDs from one archive; non-NFC content hashes deterministically but leaves the ADDRESSING layer split, since Anchors and References §3 defines character offsets over NFC text. **What this changes in practice:** a decomposed (NFD) string — routine on macOS, and emitted by several IME pipelines — previously loaded silently, with the canonicalization throw swallowed by the document-ID recompute's catch and `manifest.id` left unverified; it is now a REJECT in every state. Content Blocks §6.2's "Implementations MUST support: All Unicode normalization forms" is qualified in the same erratum, since read literally it obliged a reader to accept the content §4.3.2 forbids. (2) The **content root envelope** (Content Blocks §2.2) gains a §5.4.2 row and a §7.1 structural rule: a content part that parses but is not an object, or whose `version` or `blocks` is absent or of the wrong JSON type, REJECTs. The mistyped-`blocks` arm is the one that matters — every content-level row in the §5.4.2 table is reached by walking `blocks`, so a non-array withdraws all of them at once while the document id stays computable and a signature over it still verifies, which two independent implementations both demonstrated. The root stays OPEN (no `additionalProperties`), and a value-invalid `version` such as `"0.1.0"` is deliberately left unreported: §5.4.2 assigns it no row, and its version rows govern the manifest `cdx` field rather than the content model. §5.4's preamble gains Content Blocks, absent from it until now
- **Footnote marks are now resolved**, taking State Machine §5.4.2's extension-cross-reference row from three covered arms to four. Semantic Extension §4.5.2 is implemented as written: a `footnote` mark resolves to its `semantic:footnote` block by `id` when both carry one (id match taking precedence), otherwise by its `number` or `symbol` marker. Two codes, because the failures are different — `CDX-E-FOOTNOTE-REFERENCE-DANGLING` when nothing matches, and `CDX-E-FOOTNOTE-REFERENCE-AMBIGUOUS` when a marker matches more than one block, which §4.5.2 makes a WARNING while sending the reader to the first block in document order. The namespace is purely in-document, so unlike the citation and glossary arms it has no side file and therefore no indeterminate case. One reading is recorded rather than settled: where a mark carries an `id` matching no block, this implementation falls back to the marker instead of reporting immediately — §4.5.2's “resolves … by a single key” supports the strict reading at least as well — arguably better, since it is the only reading under which the section's MUST can be violated at all. The choice constrains nobody else: no published fixture or vector carries the disputed shape, and the comparator is a subset check, so a reader implementing the strict reading still passes the corpus. The divergence is warn-vs-silent, not WARNING-vs-WARNING
- **A `semantic:term` and a `semantic:footnote` block's `id` is left as authored** through canonicalization (Document Hashing §4.3.1 item 5; DD-022). Both blocks are the *defining* side of a reference that addresses a separate namespace and is itself never relabeled — a `glossary` mark's `ref` and a `semantic:term` `see` resolve against a term block's `id` (Semantic Extension §8.3 rule 2), a `footnote` mark against a `semantic:footnote` block (§4.5.2) — so relabeling only the definition left both rules unsatisfiable on the canonical form: the block became `b0` while the reference still named `term-algorithm`. Item 5's previous text asserted the opposite ("still has its own block `id` relabeled like any other block id") and is corrected. **Membership is unchanged**: a preserved id remains in the shared uniqueness-and-anchor namespace, a duplicate is still a canonicalization error, and a Content Anchor URI still resolves against it — only the renaming skips it, which is why §8.3 rule 2 and §4.5.2 needed no rewording. Two consequences are stated normatively rather than left implicit: a preserved id MUST NOT itself spell a canonical name (`b` followed by digits), because duplicate detection compares *authored* ids and so cannot see an authored `b0` colliding with a generated one; and the `b<n>` sequence **compacts** over a preserved occurrence rather than reserving an index, since reserving is equally implementable and would give identical content a different document ID. This **changes the document ID** of any document carrying a term or footnote block id, including two committed examples. Membership in the exception is keyed on block `type`, departing from item 5's "keyed on WHERE an id sits" principle of necessity — a term block's id sits exactly where any other block id does
- **Mark re-sorting is now scoped to a text node's `marks`, matching §4.3.1 item 3.** Item 3 is stated "within each text node" and the canonical transform normalizes marks under the text-node case alone, but the identifier-rewriting pass re-sorted and de-duplicated *every* array named `marks`, wherever it sat. A JSON-LD block annotation and a CSL bibliography entry both admit arbitrary members, so a `marks` array carried inside one was being normalized although the canonical form never touches it — two documents differing only in that array's order collapsed onto a single document ID. Found while closing the early-return hole below, which made the mis-scoped pass reachable for documents that define no ids and so exposed it generally
- **An unresolved `#b<digits>` reference is now rejected in a document that defines no ids at all.** §4.3.1 item 5 has always made such a reference a canonicalization error unconditionally, but the reference implementation returned early when the identifier namespace was empty, so the rewriting pass — which enforces the prohibition — never ran: a dangling `#b0` was accepted in a document with no ids and rejected in the same document with one id added. A document carrying only preserved ids takes the same path, so the fix precedes the change above rather than following it
- **Specification errata (five decisions transcribed into normative text).** Each closes a place where the conformance suite had to record a *reading* because §5.4.2 assigned no row or the specification contradicted itself. (1) **Absent metadata is a manifest defect, not a metadata defect** — §5.4.2's metadata row is now explicitly PART-level (a Dublin Core part referenced but absent or unparseable, or a missing required term), and an absent or mistyped `metadata`/`metadata.dublinCore` *field* falls under the manifest row instead. This is a normative TIGHTENING: a manifest declaring no `metadata` previously loaded with a warning and is now REJECT, which is what the schema always implied, `metadata` being required and `dublinCore` required within it. (2) **The out-of-hash extension-data row's examples corrected** — a semantic bibliography or glossary and an academic numbering configuration are declared as `{path, hash}` pairs that the manifest projection binds, so they were never "path-only" and the row's own qualifier excluded them; the hash-bound row governs, making them INTEGRITY-ERROR when frozen rather than WARNING. That row keeps genuinely path-only data such as `metadata.jsonld`. The HASH-BOUND row correspondingly gains "or unparseable" (excluding the `content` part, which its own row rejects, and the unobtainable-bytes cases of notes 5 and 6), so a projection-bound side file that is present but will not parse is not stranded between the two. The academic extension's own integrity note, which asserted the opposite disposition for `numbering.json`, is corrected to match. (3) **A declared asset-index path that diverges from the derived location is now REJECT** — Asset Embedding §3.1 stated the equality as a MUST and then resolved a disagreement leniently ("the derived path governs"); that sentence is deleted and §5.4.2 gains a REJECT row, because a divergence leaves the document ambiguous — a reader honouring the declaration and one honouring the derivation resolve the category's assets differently — and splits identity from attestation, the projection binding the declared path's hash while the document ID inherits the asset hashes listed in the file at the derived path. No projected bytes change: for every loadable document the two paths name one file. The row states the comparison rule (§4.3.1 path normalization) so "does not equal" is not left to the reader. (4) **`flowElement.blockIds` named** — Presentation Layers §13.4 and the dangling-presentation-reference row enumerated only `blockId` and `blockRefs`, though a flow element's `blockIds` references content blocks identically (§6.4). §13.4 now names all three and scopes the completeness claim to fields *within a presentation-layer or precise-layout file*, since a `presentation:reference` block's `target` also addresses a content block but lives in the content tree rather than a presentation file (which row disposes of a dangling one is a separate question the erratum does not settle); the `blockId` parenthetical also picks up `preciseElement` (§12.3), which is a different type from `pageElement`. No behavioural change. (5) **A dedicated §5.4.2 row for an undeclared presentation or precise-layout file** — WARNING in draft/review, INTEGRITY-ERROR when frozen or published, replacing a disposition previously inferred from the §5.4.2 preamble and Presentation Layers §12. The row states the membership test the disposition turns on (a precise layout carries `presentationType`, a reactive presentation a `type` of `paginated`, `continuous`, or `responsive`; any other file under `presentation/` stays IGNORE) and the unrecognized-file row is carved out to match, so the two no longer both reach one artifact. A second normative TIGHTENING: §12's "SHOULD be surfaced as an integrity concern" becomes a MUST, since an INTEGRITY-ERROR obliges a reader to surface the failure (§5.4.1) and a SHOULD cannot support that; §12 also now states that an undeclared *reactive* presentation file is covered, which it previously left to the §5.4.2 preamble alone
- Container Format §3.2's compression-method table is now stated to be the **complete permitted set**, and a reader MUST NOT infer a method from the data (in particular MUST NOT treat an unrecognized method as Deflate). This is a normative NARROWING: "MAY use the following" granted permission for those three methods without by itself forbidding others, and §3.1's APPNOTE.TXT conformance defines BZIP2, LZMA, XZ and PPMd — so an archive using one of those was arguably conformant and now is not. Two new State Machine §5.4.2 rows dispose of the closed set (a forbidden method, and an entry that will not decode under a permitted one — both REJECT), and a new note 6 covers the opposite case: an entry using a PERMITTED method the reader has not implemented (Zstandard is RECOMMENDED, not required) is not a defect, is reported integrity-indeterminate, and MUST NOT fire the missing-part rows — mirroring note 5 for encrypted parts, including its document-level conclusion where the entry carries required or hash-bound content. §5.4.1 gains a paragraph stating that integrity-indeterminate is not one of the four dispositions. Motivated by a reference-reader defect: treating every non-Store method as Deflate meant a Zstandard entry threw, the throw was swallowed, and the archive reported clean with its CRC-32 and every hash over those bytes unverified
- Content schema now references legal extension marks (`legal:cite`)
- Document maturity tiers introduced (Introduction §1.8.1: Hardened / Draft / Experimental) and applied — every core doc, extension, and profile carries a `Maturity` header (trust core: Document Hashing, State Machine, Provenance, Security extension → Hardened); Provenance §5.3–5.4 proof shapes and the standalone §6.4 blockchain timestamp type are marked Experimental (the latter a candidate for extraction, with the §6.5 aggregated anchor's use of its rules staying normative); README Roadmap gains a "Deferred capabilities" section aggregating the disclosed-not-closed items with pointers; OQ-005 (authenticated annotations) and OQ-006 (counter-signatures/order binding) added to the design-decisions register
- Security extension: hybrid PQC signing specified as a concrete profile (two independent signatures — classical + ML-DSA-65 — bound via `signaturePolicy.requiredSigners`; §8.2), replacing an unspecified capability claim; new §4.7 defines sign+encrypt composition (sign-then-encrypt only, logical plaintext manifest references, decrypt-incapable consumers fail closed); §5.3 permission vocabulary explicitly labeled workflow declarations, not enforcement; §9.8 lifecycle-downgrade disclosure upgraded with a reduction argument showing the residual is minimal (every downgraded presentation is honest-signature reuse, a fresh pinned-credential attestation of genuine content, or unsigned content — never tampered content presented as signed; see DD-021, which records the considered-and-rejected review-state projection binding); §4.7 also reconciles encrypted-part existence with the core missing-part dispositions (new State Machine note 5); introduction design goal 3 tightened to match §9.8 (frozen/published signatures bind state)
- Block-level Merkle tree hardened to the tagged `cdx-bmt-1` construction (core 09 §4.2–4.3): RFC 6962-style leaf/internal domain separation (`0x00`/`0x01`), odd nodes promoted instead of duplicated — closing the two previously disclosed defects (CVE-2012-2459-pattern duplication, leaf/internal ambiguity). The §5.2 block-proof fold is decoupled from the §6.5 aggregated-timestamp fold (which stays untagged raw concatenation, fixed by external aggregators). Adds a `construction` wire identifier, a `block-index.schema.json`, the `scripts/lib/block-merkle.ts` reference implementation with independent-oracle KATs, the `check:block-merkle` gate, and a worked `content/block-index.json` in the comprehensive-document example. The root remains advisory (unbound by the document ID and manifest projection); see DD-020
